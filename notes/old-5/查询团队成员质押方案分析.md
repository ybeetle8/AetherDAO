# 查询团队成员质押方案分析

## 需求

查询地址 `0xB6d86540BEBEd318f7bCf42bcE9BAA19b500BD39` 下面所有直推地址，以及每个地址上的每笔质押记录。

## 问题

合约中 `_children` 映射是 `private` 的，**没有公开函数可以直接返回某地址的下级地址列表**。

```solidity
mapping(address => address[]) private _children;  // 私有，无 getter
```

能拿到的只有数量：
- `getReferralCount(address)` → 返回直推人数
- `getTeamPerformanceDetails(address)` → 返回团队人数等

## 解决方案

### 方案一：通过链上事件查询（推荐）

每次绑定推荐关系时，合约会发出事件：

```solidity
event ReferralBound(address indexed user, address indexed referrer, uint256 timestamp);
event AdminReferralBound(address indexed user, address indexed referrer, address indexed admin, uint256 timestamp);
```

**思路：**
1. 扫描所有 `ReferralBound` 和 `AdminReferralBound` 事件
2. 筛选 `referrer == 目标地址` 的事件
3. 提取出所有 `user` 地址 → 这就是直推列表
4. 对每个地址调用 `getUserStakeRecords(address)` 获取质押明细

**优点：** 准确、完整、无需额外权限、纯读取不需要私钥
**缺点：** 需要扫描历史区块，RPC 有区块范围限制，需要分段查询

#### RPC 可行性验证（已测试）

使用项目现有的 pinax RPC 实测结果：

| 测试 | 区块范围 | 结果 |
|------|---------|------|
| 5,000 块 | ✅ 成功 | 找到 1 条事件 |
| 100,000 块 | ✅ 成功 | 找到 3 条事件 |
| 500,000 块 | ❌ 失败 | `query exceeds max block range 100000` |

**结论：pinax RPC 单次查询上限为 100,000 块。**

#### 区块数估算

BSC 出块速度约 3 秒/块：

| 时间范围 | 约需区块数 | 需要分几段 |
|---------|-----------|-----------|
| 1 天 | 28,800 块 | 1 段（一次查完） |
| 3 天 | 86,400 块 | 1 段（一次查完） |
| 7 天 | 201,600 块 | 3 段 |
| 12 天（部署至今） | 345,600 块 | 4 段 |

#### 最终结论

**完全可行！** 合约部署至今才 12 天，只需分 4 段查询即可覆盖全部历史。脚本自动分段，用户无感知。即使只查最近几天，一次 RPC 调用就够了。

### 方案二：通过 BscScan API 查询事件

用 BscScan 的 getLogs API 查询事件，不受 RPC 区块范围限制。

**优点：** 简单，不受区块范围限制
**缺点：** 依赖 BscScan API Key，有频率限制

### 方案三：已知地址列表

如果你已经知道（或能从其他渠道获得）这些直推地址，可以直接硬编码到脚本里查询。

## 实现方案（方案一）

### 脚本执行流程

```
1. 获取当前区块号
2. 计算起始区块（当前块 - 345600，覆盖部署至今全部历史）
3. 分段查询事件（每段 100,000 块）:
   - 扫描 ReferralBound 事件，过滤 referrer == 目标地址
   - 扫描 AdminReferralBound 事件，过滤 referrer == 目标地址
4. 合并去重 → 得到直推地址列表
5. 对每个直推地址调用 getUserStakeRecords() → 获取质押明细
6. 汇总输出
```

### 技术细节

- RPC: 使用项目现有的 pinax BSC RPC（无需额外配置）
- 分段策略: 每段 95,000 块（留余量，避免边界问题）
- 事件过滤: 利用 indexed 参数在 RPC 层面过滤，减少数据传输
- 无需私钥: 纯 view 调用 + 事件查询

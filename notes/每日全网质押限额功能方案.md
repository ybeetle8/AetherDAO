# 每日全网质押限额功能方案

## 1. 需求概述

在质押(`stake`)时新增**全网每日限额**机制：

- **每日全网限额**: 50,000 USDX（所有用户共享）
- **刷新时间**: 北京时间每天下午 14:00（UTC+8 14:00 = UTC 06:00）
- **查询接口**: 提供 view 函数，可读取当前周期剩余可用额度

## 2. 现有限额机制分析

当前合约中已有以下限制，新功能需要与它们共存：

| 限制 | 值 | 位置 |
|------|----|------|
| 单笔最小质押 | 100 USDX | `MIN_STAKE_AMOUNT` |
| 单笔最大质押（动态） | min(池子1% - 近1分钟流入, 1000) | `maxStakeAmount()` |
| 用户累计上限 | 10,000 USDX | `MAX_USER_TOTAL_STAKE` |
| 7天质押 | 每用户仅一次 | `hasUsed7DayStake` |

新增的每日全网限额是一个**独立维度**的检查，在 `_validateStakeParameters` 中追加即可。

## 3. 合约修改方案

### 3.1 新增常量

```solidity
// 每日全网质押限额 50,000 USDX
uint256 internal constant DAILY_NETWORK_STAKE_LIMIT = 50_000 ether;

// 刷新时间: UTC 06:00 (= 北京时间 14:00)
uint256 internal constant DAILY_RESET_HOUR_UTC = 6;

// 一天的秒数
uint256 internal constant SECONDS_PER_DAY = 86400;
uint256 internal constant SECONDS_PER_HOUR = 3600;
```

### 3.2 新增状态变量

```solidity
// 当前周期已质押总量
uint256 public dailyStakedAmount;

// 当前周期的起始时间戳（上一次刷新时间点）
uint256 public dailyPeriodStart;
```

### 3.3 核心逻辑 - 周期判断函数

```solidity
/// @notice 计算当前周期的起始时间戳（最近一次 UTC 06:00）
function _getCurrentPeriodStart() internal view returns (uint256) {
    // 从 block.timestamp 计算今天 UTC 06:00 的时间戳
    uint256 todayResetTime = (block.timestamp / SECONDS_PER_DAY) * SECONDS_PER_DAY
                             + DAILY_RESET_HOUR_UTC * SECONDS_PER_HOUR;

    // 如果当前时间还没到今天的刷新点，则当前周期从昨天的刷新点开始
    if (block.timestamp < todayResetTime) {
        return todayResetTime - SECONDS_PER_DAY;
    }
    return todayResetTime;
}
```

### 3.4 核心逻辑 - 限额检查与更新

在 `stake()` 函数中（`_validateStakeParameters` 之后，`_swapAndAddLiquidity` 之前）插入：

```solidity
// 检查并更新每日全网限额
_checkAndUpdateDailyLimit(_amount);
```

新增内部函数：

```solidity
function _checkAndUpdateDailyLimit(uint256 _amount) private {
    uint256 currentPeriodStart = _getCurrentPeriodStart();

    // 如果进入了新周期，重置计数
    if (dailyPeriodStart < currentPeriodStart) {
        dailyPeriodStart = currentPeriodStart;
        dailyStakedAmount = 0;
    }

    // 检查是否超出限额
    require(
        dailyStakedAmount + _amount <= DAILY_NETWORK_STAKE_LIMIT,
        "Exceeds daily network stake limit"
    );

    // 更新已质押总量
    dailyStakedAmount += _amount;
}
```

### 3.5 新增 View 函数

```solidity
/// @notice 获取当前周期剩余可用质押额度
/// @return remaining 剩余额度 (USDX, 18 decimals)
function getDailyStakeRemaining() external view returns (uint256 remaining) {
    uint256 currentPeriodStart = _getCurrentPeriodStart();

    // 如果已进入新周期，限额还未被消耗
    if (dailyPeriodStart < currentPeriodStart) {
        return DAILY_NETWORK_STAKE_LIMIT;
    }

    // 当前周期内的剩余额度
    if (dailyStakedAmount >= DAILY_NETWORK_STAKE_LIMIT) {
        return 0;
    }
    return DAILY_NETWORK_STAKE_LIMIT - dailyStakedAmount;
}

/// @notice 获取当前周期已质押总量
/// @return used 已使用额度 (USDX, 18 decimals)
function getDailyStakeUsed() external view returns (uint256 used) {
    uint256 currentPeriodStart = _getCurrentPeriodStart();

    if (dailyPeriodStart < currentPeriodStart) {
        return 0;
    }
    return dailyStakedAmount;
}

/// @notice 获取下次刷新的时间戳
/// @return nextReset 下次刷新的 Unix 时间戳
function getNextDailyResetTime() external view returns (uint256 nextReset) {
    return _getCurrentPeriodStart() + SECONDS_PER_DAY;
}
```

### 3.6 新增 Error 和 Event

在 `IStaking.sol` 接口中新增：

```solidity
/// @notice 超出每日全网质押限额
error ExceedsDailyNetworkStakeLimit();

/// @notice 每日限额周期重置事件
event DailyStakeLimitReset(uint256 periodStart, uint256 timestamp);
```

> **注**: 也可以使用 `require + string` 替代自定义 error，与现有 7天质押检查风格保持一致。根据合约现有风格，部分校验用 `revert CustomError()`，部分用 `require()`。建议用 `require()` 保持与相邻代码一致。

## 5. 关键设计决策

### 5.1 为什么不用 `block.timestamp % 86400` 简单取模？

直接取模得到的是 UTC 00:00 的周期。我们需要 UTC 06:00 (北京时间 14:00) 作为分界点，所以需要额外的偏移计算。

### 5.2 重置触发机制 — 惰性重置（Lazy Reset）详解

**核心原则：没有任何人需要手动触发重置，也没有定时任务，一切都是无感自动完成的。**

#### 触发方式

重置不是在"北京时间 14:00 那一刻"发生的，而是**下一次有人调用 `stake()` 时顺带完成的**。具体来说：

1. 用户调用 `stake()` 质押
2. 合约内部调用 `_checkAndUpdateDailyLimit()`
3. 该函数先计算"当前时间属于哪个周期"（通过 `_getCurrentPeriodStart()`）
4. 对比存储中的 `dailyPeriodStart`（上次记录的周期起点）
5. **如果发现已经跨入新周期** → 自动把 `dailyStakedAmount` 清零，更新 `dailyPeriodStart`
6. 然后正常执行限额检查

用户完全感知不到"重置"这个动作，对他来说就是正常质押。

#### 时间线示例


#### view 函数同样无感

`getDailyStakeRemaining()` 等查询函数也使用相同的周期判断逻辑。即使存储中的 `dailyPeriodStart` 还是昨天的值，view 函数也能**正确返回新周期的额度**：

```
第2天 15:00（还没有人质押，存储未更新）：
  - 存储: dailyPeriodStart = 第1天14:00, dailyStakedAmount = 1500
  - 计算: 当前周期起点 = 第2天14:00
  - 判断: dailyPeriodStart(第1天14:00) < 第2天14:00 → 已跨周期
  - 返回: 剩余额度 = 50000（满额）  ← 正确！
```

view 函数不写存储，只是用同样的判断逻辑"假装"重置了。真正的存储重置会在下次 `stake()` 时完成。

#### 为什么选择这种方式

| 方案 | 缺点 |
|------|------|
| 定时任务 (Keeper/Cron) | 需要链下服务，增加运维复杂度，存在单点故障 |
| Owner 手动调 reset() | 需要人工操作，可能遗忘，14:00 必须准时 |
| 任何人都能调的 reset() | 多余的公开函数，增加攻击面 |
| **惰性重置 (本方案)** | **无外部依赖，零运维，完全链上自治** |

### 5.3 Gas 开销分析

- `_getCurrentPeriodStart()`: 纯计算，无存储读写，约 200 gas
- `_checkAndUpdateDailyLimit()`: 最多 2 次 SSTORE（周期重置时），约 5,000-20,000 gas
- 对于正常质押操作（~500,000+ gas），新增开销可忽略不计

## 8. 风险评估

| 风险 | 等级 | 说明 |
|------|------|------|
| 时间戳操纵 | 低 | BSC 出块时间稳定(~3s)，矿工操纵范围有限，且限额为 50,000 量级，不存在精确套利空间 |
| 周期边界竞态 | 无 | 单交易内原子执行，不存在竞态问题 |
| 存储碰撞 | 无 | 新增状态变量追加在末尾，不影响已有 storage layout |
| 与现有限制冲突 | 无 | 独立检查维度，不修改任何现有校验逻辑 |

# AetherDAO 团队等级系统详解（双维度版本）

## 一、概述

AetherDAO 的团队等级系统是一个基于**双维度**的分级奖励机制。用户的等级由两个条件共同决定：
1. **Team KPI（团队业绩）**：下级团队的累计质押总额
2. **个人质押价值**：用户当前的质押金额

用户的最终等级取两个维度中的**较低者**，确保用户既有团队贡献，也有个人投入。

### 核心特点

- **9 个等级**：V1 到 V9
- **双维度判定**：Team KPI + 个人质押，取最小值
- **动态计算**：等级根据实时数据自动计算
- **差额分配**：高等级成员获得差额奖励，避免重复分配
- **激励机制**：等级越高，奖励比例越高
- **防止投机**：必须有个人投入才能获得高等级

### 2.2 设计规律

#### Team KPI 门槛增长规律
- 采用约 **3 倍增长**规律
- 3K → 10K → 30K → 100K → 300K → 1M → 3M → 10M → 30M
- 使等级提升路径更加平滑和可预测

#### 个人质押门槛增长规律
- 采用 **混合增长**规律（2x-3x 交替）
- 100 → 300 (3x) → 600 (2x) → 1,000 (1.67x) → 3,000 (3x) → 6,000 (2x) → 10,000 (1.67x) → 15,000 (1.5x) → 20,000 (1.33x)
- 初级门槛低，鼓励参与；高级门槛适中，保持挑战性

#### 奖励增长规律
- 采用 **线性递增 4%** 规律
- 3% → 7% → 11% → 15% → 19% → 23% → 27% → 31% → 35%
- 每提升一级，奖励比例增加 4%

## 三、双维度等级判定

### 3.1 判定规则

**用户最终等级 = min(基于 Team KPI 的等级, 基于个人质押的等级)**

#### 判定流程

```
步骤 1: 检查是否是 rootAddress
  - 如果是 → 等级 = 0

步骤 2: 基于 Team KPI 计算等级
  teamKpiTier = 根据 teamTotalInvestValue 匹配等级

步骤 3: 基于个人质押计算等级
  personalStakeTier = 根据 currentStakeValue 匹配等级

步骤 4: 取两者最小值
  finalTier = min(teamKpiTier, personalStakeTier)

步骤 5: 返回最终等级
  return finalTier
```

**代码位置**：[StakingBase.sol:1272-1287](../contracts/AE-Staking/src/abstract/StakingBase.sol#L1272-L1287)

```solidity
function _getUserTier(address user) private view returns (uint8 tier) {
    // rootAddress has no tier
    if (user == rootAddress) {
        return 0;
    }

    // Get tier based on Team KPI
    uint256 teamKPI = getTeamKpi(user);
    uint8 teamKpiTier = _getTierByTeamKpi(teamKPI);

    // Get tier based on personal stake
    uint256 personalStake = currentStakeValue(user);
    uint8 personalStakeTier = _getTierByPersonalStake(personalStake);

    // Return the minimum of both tiers
    return teamKpiTier < personalStakeTier ? teamKpiTier : personalStakeTier;
}
```

### 3.2 判定示例

#### 示例 1：个人质押限制等级

```
用户 A:
- Team KPI: 500,000 USDT → 基于 Team KPI 等级 = V4 (≥100,000)
- 个人质押: 500 USDT → 基于个人质押等级 = V2 (≥300, <600)
- 最终等级: min(V4, V2) = V2 ✅
- 奖励比例: 7%

说明：虽然团队业绩达到 V4，但个人质押只有 V2，所以最终等级是 V2
```

```

- 最终等级: min(V1, V7) = V1 ✅
- 奖励比例: 3%

说明：虽然个人质押达到 V7，但团队业绩只有 V1，所以最终等级是 V1
```

#### 示例 3：两者都达标

```solidity
function _getTierByTeamKpi(
    uint256 teamKPI
) private view returns (uint8 tier) {
    IStaking.TeamTier[9] memory tiers = _getTeamTiers();
    for (uint256 i = 0; i < tiers.length; ) {
        if (teamKPI >= tiers[i].threshold) {
            return uint8(9 - i);
        }
        unchecked {
            ++i;
        }
    }
    return 0;
}
```

## 五、Team KPI（团队业绩）

### 5.1 定义

**Team KPI = 团队总投资价值 (teamTotalInvestValue)**

这是用户整个下级团队（推荐链，最多 20 层）的累计质押金额总和。

**代码位置**：[StakingBase.sol:670-672](../contracts/AE-Staking/src/abstract/StakingBase.sol#L670-L672)

```solidity
function getTeamKpi(address _user) public view returns (uint256) {
    return teamTotalInvestValue[_user];
}
```

### 5.2 Team KPI 更新机制

#### 质押时增加

当用户质押时：
1. 获取该用户的推荐链（最多 20 层）
2. 将质押金额累加到推荐链上每个地址的 `teamTotalInvestValue`

**代码位置**：[StakingBase.sol:801-817](../contracts/AE-Staking/src/abstract/StakingBase.sol#L801-L817)

#### 解质押时减少

当用户解质押时：
1. 获取该用户的推荐链
2. 将解质押的**本金**从推荐链上每个地址的 `teamTotalInvestValue` 中扣除

**注意**：只扣除本金，不扣除利息部分。

### 5.3 Team KPI 计算示例

```
假设推荐关系：
A (rootAddress)
└─ B (推荐人)
   └─ C (推荐人)
      └─ D (用户)

当 D 质押 1,000 USDT 时：
- D 的 teamTotalInvestValue 不变（自己的质押不计入）
- C 的 teamTotalInvestValue += 1,000
- B 的 teamTotalInvestValue += 1,000
- A 的 teamTotalInvestValue += 1,000

当 C 质押 5,000 USDT 时：
- C 的 teamTotalInvestValue 不变
- B 的 teamTotalInvestValue += 5,000 (现在是 6,000)
- A 的 teamTotalInvestValue += 5,000 (现在是 6,000)

此时（假设 B 和 C 的个人质押都足够）：
- B 的 Team KPI = 6,000 USDT → Team KPI 等级 = V1
- C 的 Team KPI = 1,000 USDT → Team KPI 等级 = V0
```

## 六、个人质押价值

### 6.1 定义

**个人质押价值 = currentStakeValue(user)**

这是用户当前所有质押记录的本金总和。

### 6.2 计算方式

```solidity
function currentStakeValue(address user) public view returns (uint256) {
    // 遍历用户所有质押记录，累加本金
    uint256 totalValue = 0;
    for (uint256 i = 0; i < userStakeRecords[user].length; i++) {
        totalValue += userStakeRecords[user][i].amount;
    }
    return totalValue;
}
```

### 6.3 动态变化

- **质押时增加**：新增质押记录，个人质押价值增加
- **解质押时减少**：移除质押记录，个人质押价值减少
- **实时计算**：每次判定等级时都会重新计算

## 七、奖励分配机制

### 7.1 差额分配原则

当用户解质押时，系统会根据推荐链上各成员的等级分配团队奖励。

**核心原则**：
1. **差额分配**：高等级成员获得 (自己等级比例 - 已分配比例) 的奖励
2. **等级唯一性**：每个等级只能被一个成员获得
3. **从下往上遍历**：从直接推荐人开始，向上遍历推荐链
4. **最高 35%**：团队奖励总比例不超过 35%
5. **无需 Preacher 检查**：等级已经包含了个人质押要求

### 7.2 奖励分配示例

#### 示例：标准差额分配

```
推荐链（从下往上）：
- 位置 0: Alice (V3, 11%)
- 位置 1: Bob   (V5, 19%)
- 位置 2: Carol (V2, 7%)
- 位置 3: Dave  (V7, 27%)
- 位置 4: Eve   (V9, 35%)

利息总额：1,000 USDT
团队奖励池：1,000 * 35% = 350 USDT

分配过程：
1. Alice (V3, 11%):
   - 差额 = 11% - 0% = 11%
   - 奖励 = 1,000 * 11% = 110 USDT
   - 累计已分配 = 11%

2. Bob (V5, 19%):
   - 差额 = 19% - 11% = 8%
   - 奖励 = 1,000 * 8% = 80 USDT
   - 累计已分配 = 19%

3. Carol (V2, 7%):
   - V2 等级 (7%) < 累计已分配 (19%)
   - 差额 = 0%
   - 奖励 = 0 USDT
   - 跳过

4. Dave (V7, 27%):
   - 差额 = 27% - 19% = 8%
   - 奖励 = 1,000 * 8% = 80 USDT
   - 累计已分配 = 27%

5. Eve (V9, 35%):
   - 差额 = 35% - 27% = 8%
   - 奖励 = 1,000 * 8% = 80 USDT
   - 累计已分配 = 35%
   - 达到最高比例，停止分配

总分配：110 + 80 + 80 + 80 = 350 USDT ✅
```

## 八、与旧版本的对比

### 8.1 主要变化

| 项目 | 旧版本（Preacher 机制） | 新版本（双维度机制） |
|------|------------------------|---------------------|
| 判定维度 | 单维度（Team KPI） | 双维度（Team KPI + 个人质押） |
| 个人质押要求 | 固定 1,000 USDT | 每个等级不同（100-20,000） |
| 等级判定 | 只看 Team KPI | 取两个维度的最小值 |
| Preacher 检查 | 需要 | 不需要（已包含在等级中） |
| 奖励分配检查 | 需要验证 isPreacher | 不需要（等级已验证） |

### 8.2 设计理念变化

**旧版本**：
- 只要达到 1,000 USDT，就可以获得等级（只看 Team KPI）
- 可能出现"空手套白狼"（个人投入少，团队大）

**新版本**：
- 必须同时满足 Team KPI 和个人质押两个条件
- 高等级需要相应的个人投入
- 更公平，更能激励用户平衡发展

### 8.3 优势分析

1. **更细化的控制**
   - 旧机制：只有 Preacher (1,000) 一个门槛
   - 新机制：9 个等级，每个等级都有对应的个人质押要求

2. **更公平的分配**
   - 旧机制：只要是 Preacher，就可以获得高等级（只看 Team KPI）
   - 新机制：必须个人投入和团队业绩都达标

3. **更强的激励**
   - 旧机制：达到 1,000 后，个人质押再多也没有额外好处
   - 新机制：个人质押越多，能达到的等级上限越高

4. **更好的风险控制**
   - 旧机制：可能出现"空手套白狼"（个人投入少，团队大）
   - 新机制：高等级必须有相应的个人投入

## 十、注意事项

### 10.1 对用户的影响

1. **等级可升可降**：Team KPI 和个人质押都会实时变化，等级会动态调整
2. **需要平衡发展**：必须同时关注团队发展和个人投入
3. **推荐关系重要**：绑定推荐人后无法更改（锁定机制）
4. **先到先得**：相同等级的成员，推荐链中位置靠前的优先获得奖励

### 10.2 对开发的影响

1. **Gas 消耗**：增加了个人质押等级计算，但移除了 Preacher 检查，总体变化不大
2. **代码简化**：移除了 Preacher 相关的检查和事件
3. **逻辑清晰**：双维度判定逻辑简单明了

### 10.3 经济模型考虑

1. **激励平衡发展**：用户需要同时关注团队和个人
2. **减少投机行为**：纯推广、不投入的行为被抑制
3. **提高系统稳定性**：更多资金锁定在系统中
4. **公平性**：高等级需要真正的投入

# [P0] 质押中途提取利息后，解押时复利多算问题

## 问题描述

用户在质押期间通过 `withdrawInterest()` 提取了利息，但最终 `unstake()` 解押时，复利仍然按照**从未提取过利息**的方式计算。虽然 `_burn()` 中有 `reward -= alreadyWithdrawn` 的修复（C-02），但这个减法**不足以修正复利膨胀**的根本问题。

## 问题根因

### 核心公式

`_calculateStakeReward()` (StakingBase.sol:1555-1584):

```solidity
UD60x18 principalAmount = ud(stakeRecord.amount);  // 始终使用原始本金
UD60x18 compoundedAmount = principalAmount.mul(
    baseInterestRate.powu(compoundPeriods)           // 全周期复利
);
```

这个公式的含义是：**本金 × (1 + 日利率)^天数**

问题在于：提取利息后，已提取的利息不再参与复利增长，但公式仍然假设所有利息都在系统中持续复利。

### 数值举例（365天档，日复利2%）

假设用户质押 1000 USDX，选择365天档（日复利率 1.02）。

**第100天 - 用户提取利息：**
- 系统计算总价值 = 1000 × 1.02^100 = 7,244.6 USDX
- 利息 = 7,244.6 - 1,000 = 6,244.6 USDX
- 用户提取全部利息 6,244.6
- `withdrawnInterest[user][idx] = 6,244.6`

**第365天 - 用户解押：**
- 系统计算总价值 = 1000 × 1.02^365 = 1,377,408 USDX
- `_burn()` 中：`reward = 1,377,408 - 6,244.6 = 1,371,163.4`
- **用户实际总获取 = 6,244.6（第100天已提） + 1,371,163.4（解押获取）= 1,377,408 USDX**

**正确值应该是多少？**

用户在第100天提走了 6,244.6 的利息，之后只有本金 1000 继续赚复利：

- 第0-100天收益：6,244.6（已提取）
- 第100-365天收益：1000 × 1.02^265 - 1000 = 189,764.5
- **正确总获取 = 6,244.6 + 1000 + 189,764.5 = 197,009.1 USDX**

**差距：用户多拿了 1,377,408 - 197,009 ≈ 1,180,399 USDX！**

### 为什么现有的 C-02 修复不够？

`_burn()` 中的修复（StakingBase.sol:1289-1294）：

```solidity
uint256 alreadyWithdrawn = withdrawnInterest[sender][index];
if (alreadyWithdrawn > 0) {
    reward -= alreadyWithdrawn;
}
```

这只是从最终的全周期复利结果中**线性减去**已提取金额。但真正的问题是：已提取的利息在提取之后就不应该继续产生复利。简单减法无法消除指数增长带来的差异。

## 解决方案

### 方案一：分段复利（推荐）

**核心思路**：每次提取利息时，记录一个"检查点"，将复利计算拆分为多个独立时间段。

**数据结构变更**：

```solidity
// 新增：利息提取检查点
struct InterestCheckpoint {
    uint40 timestamp;       // 提取时间
    uint256 withdrawnAmount; // 本次提取的利息金额（AE计价）
}

// 每个质押记录关联一组检查点
mapping(address => mapping(uint256 => InterestCheckpoint[])) public interestCheckpoints;
```

**新的计算逻辑**：

```
总价值 = 分段计算结果

如果没有检查点：
    总价值 = principal × rate^(totalDays)

如果有检查点 [cp1, cp2, ...]：
    第一段：principal × rate^(cp1.time - stakeStart) = V1
    提取后剩余本金：principal（利息被拿走，本金不变）
    第二段：principal × rate^(cp2.time - cp1.time) = V2
    ...
    最后一段：principal × rate^(now - lastCp.time) = Vn

    总价值 = Σ(Vi - principal) + principal  （每段利息之和 + 本金）
    已提取 = Σ(cpi.withdrawnAmount)
    可用 = 总价值 - 已提取 - principal  （剩余未提利息）
```

简化理解：**每次提取利息后，复利重新从本金开始计算**。

**优点**：
- 数学上精确
- 不影响从未提过利息的用户（无检查点 = 原逻辑）
- 可以支持任意次中途提息

**缺点**：
- 需要遍历检查点数组，gas 随提取次数增加
- 合约存储变更较大

### 方案二：记录"等效本金"

**核心思路**：每次提取利息时，不记录检查点，而是将 `stakeRecord.amount` 重置为当前本金（不含已取利息），同时重置 `stakeTime` 为当前时间。

**实现**：

```solidity
function withdrawInterest(uint256 stakeIndex) external {
    // ... 计算可用利息 ...

    // 提取利息后，重置质押记录
    stakeRecord.stakeTime = uint40(block.timestamp);  // 重置起始时间
    // stakeRecord.amount 不变（本金不变）

    // 不再需要 withdrawnInterest mapping
}
```

**新的解押逻辑**：

`_burn()` 中不再需要 `reward -= alreadyWithdrawn`，因为每次提息后时间已重置，复利从提息点开始重新计算。

**优点**：
- 实现极简，改动最小
- 不增加存储，gas 不变
- 不需要遍历任何数组

**缺点**：
- 重置 `stakeTime` 可能影响到期判断（`_burn()` 中的 `StakingPeriodNotMet` 检查）
- 需要额外字段记录原始到期时间
- 用户在前端看到的质押开始时间会变

### 方案三：改进等效本金（方案二的增强版，推荐实施）

在方案二基础上，新增一个字段保留原始到期时间，避免影响解押时间判断：

**数据结构变更**：

```solidity
// 在 IStaking.Record 中新增字段
struct Record {
    // ... 原有字段 ...
    uint40 compoundStartTime;  // 新增：复利起算时间（默认 = stakeTime）
}
```

**withdrawInterest 改动**：

```solidity
function withdrawInterest(uint256 stakeIndex) external {
    // 计算利息（用 compoundStartTime 而不是 stakeTime）
    uint256 totalCurrentValue = _calculateStakeReward(stakeRecord);
    uint256 availableInterest = totalCurrentValue - stakeRecord.amount;

    // 提取利息
    // ...

    // 重置复利起算时间
    stakeRecord.compoundStartTime = uint40(block.timestamp);

    // 不再需要 withdrawnInterest mapping
}
```

**_calculateStakeReward 改动**：

```solidity
function _calculateStakeReward(IStaking.Record storage stakeRecord) private view {
    // 改用 compoundStartTime
    uint40 stakeStartTime = stakeRecord.compoundStartTime;  // 原来是 stakeRecord.stakeTime
    // ... 其余逻辑不变 ...
}
```

**_burn 改动**：

```solidity
function _burn(uint256 index) private {
    // 到期判断仍用原始 stakeTime
    if (block.timestamp - stakeTime < getStakePeriod(user_record.stakeIndex))
        revert StakingPeriodNotMet();

    // 不再需要 withdrawnInterest 扣除逻辑
    // reward = _calculateStakeReward(user_record);  // 直接使用，无需修正
}
```

**优点**：
- 改动最小（新增1个字段，改3个函数）
- 数学上精确
- gas 不增加
- 不影响到期时间判断
- `stakeTime` 保持不变，前端展示无影响

**缺点**：
- Record 结构体变更，需要合约升级
- 已有的质押记录 `compoundStartTime` 默认为 0，需要兼容处理（为 0 时回退到 `stakeTime`）

## 推荐方案

**推荐方案三（改进等效本金）**，理由：

1. **改动最小**：仅新增1个字段，修改3个函数
2. **数学精确**：每次提息后复利从新起点计算，不存在多算
3. **gas 友好**：不增加循环或数组遍历
4. **向后兼容**：`compoundStartTime == 0` 时回退到 `stakeTime`，已有质押不受影响
5. **简单可审计**：逻辑直观，易于审计验证

## 需要变更的文件

| 文件 | 变更内容 |
|------|---------|
| `contracts/AE-Staking/src/interfaces/IStaking.sol` | Record 结构体新增 `compoundStartTime` 字段 |
| `contracts/AE-Staking/src/abstract/StakingBase.sol` | 1. `_calculateStakeReward()` 改用 `compoundStartTime` |
| | 2. `withdrawInterest()` 提取后重置 `compoundStartTime` |
| | 3. `_burn()` 移除 `withdrawnInterest` 扣除逻辑 |
| | 4. `_mintStakeRecord()` 初始化 `compoundStartTime = stakeTime` |
| | 5. `withdrawnInterest` mapping 可标记为废弃（保留兼容） |

## 紧急缓解措施

在方案实施前，可以先通过以下方式止血：

1. **暂停 `withdrawInterest()` 功能**（如果合约有 pause 机制）
2. **或者在前端隐藏中途提息入口**
3. 只要用户不在中途提取利息，解押计算就是正确的

## 测试验证要点

1. 从未提过息的用户解押 → 结果应与现在一致
2. 中途提息1次后解押 → 总获取 = 提取的利息 + 解押获取，不超过纯持有不提时的复利总值
3. 中途提息多次后解押 → 同上
4. 边界：在质押第1天提息、在到期前1天提息
5. 已有老质押记录（`compoundStartTime == 0`）的兼容性

# 推荐关系迁移方案：从 AetherReferral 到 AE-Staking

## 背景

- 老合约 `AetherReferral.sol` 已部署，存储了用户的推荐人绑定关系（无好友数据需要迁移）
- 新合约 `AE-Staking/StakingBase.sol` 内置了独立的推荐关系系统
- 两套系统的数据结构几乎一致：`_referrals`、`_children`、`_hasLocked`
- 目标：把老合约中已绑定的推荐关系，同步到新合约中

## 关键差异分析

| 对比项 | 老合约 AetherReferral | 新合约 StakingBase |
|--------|----------------------|-------------------|
| 绑定校验 | 要求推荐人已绑定 | 不要求推荐人已绑定 |
| 循环引用检查 | 有 | 无 |
| admin 批量绑定 | 有 `adminBindReferral` | 无，只有用户自己调 `lockReferral` |
| 绑定后副作用 | 无 | 会同步已有质押到推荐链的 `teamTotalInvestValue` |

新合约的 `lockReferral` 不检查推荐人是否已绑定，这意味着迁移时不需要严格按照树的层级顺序导入。

---

## 方案一：链下脚本批量调用 lockReferral（推荐）

### 思路
用 JS 脚本从老合约读取所有推荐关系，然后逐个调用新合约的 `lockReferral`。

### 问题
`lockReferral` 使用 `msg.sender` 作为绑定用户，无法由管理员代替用户调用。

### 解决方式
需要在新合约中新增一个 `onlyOwner` 的批量导入函数：

```solidity
function batchImportReferrals(
    address[] calldata users,
    address[] calldata referrers
) external onlyOwner {
    require(users.length == referrers.length, "Length mismatch");
    for (uint256 i = 0; i < users.length; i++) {
        address user = users[i];
        address referrer = referrers[i];
        if (_referrals[user] != address(0)) continue; // 已绑定则跳过
        _referrals[user] = referrer;
        _children[referrer].push(user);
        _hasLocked[user] = true;
        emit ReferralBound(user, referrer, block.timestamp);
    }
}
```

### 迁移脚本流程
1. 从老合约事件 `ReferralBound` 中扫描所有绑定记录
2. 构建 `[user, referrer]` 数组
3. 分批调用 `batchImportReferrals`（每批 50-100 个，避免 gas 超限）
4. 迁移完成后可移除该函数（或保留但加上一次性开关）

### 优点
- 实现简单，逻辑清晰
- 不依赖外部合约调用，数据直接写入
- 可以跳过已绑定用户，支持增量迁移

### 缺点
- 需要修改新合约代码，增加 admin 函数
- 如果用户已在新合约质押，导入后不会自动同步 `teamTotalInvestValue`（需要额外处理）

## 方案二：新合约读取老合约（懒加载）

### 思路
新合约保存老合约地址，在用户首次交互时自动从老合约读取推荐关系。

### 实现方式
修改 `lockReferral` 或新增 `_tryImportFromOldContract`：

```solidity
IAetherReferral public oldReferralContract;

function _tryImportFromOldContract(address user) internal {
    if (_referrals[user] != address(0)) return; // 已有绑定
    address oldReferrer = oldReferralContract.getReferral(user);
    if (oldReferrer == address(0)) return; // 老合约也没绑定

    _referrals[user] = oldReferrer;
    _children[oldReferrer].push(user);
    _hasLocked[user] = true;
    emit ReferralBound(user, oldReferrer, block.timestamp);
}
```

在质押前调用：
```solidity
function stake(...) external {
    _tryImportFromOldContract(msg.sender);
    if (_referrals[msg.sender] == address(0)) revert MustBindReferral();
    // ...
}
```

### 优点
- 用户无感，自动迁移
- 不需要一次性批量操作，gas 分散到每次用户交互
- 推荐人链也可以递归导入

### 缺点
- 增加了合约复杂度和每次交互的 gas 成本
- 老合约必须持续可用（如果老合约被暂停或销毁则失败）
- 推荐人的推荐人可能还没导入，需要递归处理整条链
- `_children` 数组可能不完整（只有交互过的用户才会被导入）

## 方案三：部署前预置数据（构造函数/初始化）

### 思路
在部署新合约时，通过初始化函数一次性写入所有推荐关系。

### 实现方式
```solidity
function initialize(
    address[] calldata users,
    address[] calldata referrers
) external onlyOwner {
    require(!initialized, "Already initialized");
    for (uint256 i = 0; i < users.length; i++) {
        _referrals[users[i]] = referrers[i];
        _children[referrers[i]].push(users[i]);
        _hasLocked[users[i]] = true;
    }
    initialized = true;
}
```

### 优点
- 一次性完成，部署后数据就绑定
- 不影响后续正常业务逻辑

### 缺点
- 如果数据量大，可能超出单笔交易 gas 上限（需要分批）
- 本质上和方案一类似，只是时机不同
- 如果合约已部署则不适用

---

## 方案对比总结

| 维度 | 方案一：批量导入 | 方案二：懒加载 | 方案三：部署时预置 |
|------|----------------|---------------|-------------------|
| 合约改动量 | 小（加一个函数） | 中（改质押逻辑） | 小（加初始化函数） |
| 迁移完整性 | 高（一次性全量） | 中（按需迁移） | 高（一次性全量） |
| 对老合约依赖 | 无（链下读取） | 有（链上调用） | 无（链下读取） |
| gas 成本 | 集中（管理员承担） | 分散（用户承担） | 集中（管理员承担） |
| 适用时机 | 合约已部署或未部署 | 合约未部署 | 合约未部署 |
| 实现复杂度 | 低 | 高 | 低 |

## 建议

如果新合约还没部署，方案一和方案三都可以，推荐方案一（批量导入函数），因为：
1. 可以分批执行，不怕 gas 超限
2. 支持增量迁移（后续老合约有新绑定也能再导入）
3. 迁移完成后函数可以保留或移除，灵活性高

如果希望用户完全无感且老合约长期可用，方案二也是可行的，但会增加合约复杂度。

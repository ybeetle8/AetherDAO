# 买入税资金分配修改方案

## 当前实现分析

### 现状
在 [AEBase.sol:728-745](contracts/AE/src/abstract/AEBase.sol#L728-L745) 中，买入交易的税费处理如下：

```solidity
uint256 burnFee = (amount * BUY_BURN_FEE) / BASIS_POINTS;        // 1%
uint256 liquidityFee = (amount * BUY_LIQUIDITY_FEE) / BASIS_POINTS; // 2%
uint256 totalFees = burnFee + liquidityFee;                       // 总计 3%
```

**当前分配方式：**
- 1% → 销毁（发送到死亡地址）
- 2% → LiquidityStaking 合约（作为 BLA 奖励）

### 问题
当前的 2% liquidityFee 是直接存入 LiquidityStaking 合约，用于流动性质押奖励。现在需要改为直接分配到两个独立的地址。

---

## 修改需求

### 新的分配方式
买入税总计 **3%**，分配如下：

- **2% → 节点分红池**：`0x06Ba6DA5d1942DA184ad3E521bC51dfF32D721d9`
- **1% → 社区分红池**：`0xeE1285c96E77f2E8CB9C38b66A0BB51b2fCE5537`

**总买入税：3%**（2% 节点 + 1% 社区）

**注意：取消原有的 1% 销毁机制**

---

## 实施方案

### 方案 A：简单直接分配（推荐）

**优点：**
- 实现简单，逻辑清晰
- Gas 消耗低
- 无需依赖其他合约
- 资金实时到账，无需额外操作
- 取消销毁机制，保持代币总量稳定

**缺点：**
- 完全移除了 LiquidityStaking 的 BLA 奖励机制
- 需要确认这两个地址是否已部署/是否为合约地址

**实施步骤：**

1. **修改配置文件** `ae-deployment-config.json`
   ```json
   "addresses": {
     ...
     "nodeRewardPool": "0x06Ba6DA5d1942DA184ad3E521bC51dfF32D721d9",
     "communityRewardPool": "0xeE1285c96E77f2E8CB9C38b66A0BB51b2fCE5537"
   }
   ```

2. **修改 AEBase.sol 常量定义**（第 206-210 行）
   ```solidity
   uint256 private constant BUY_NODE_REWARD_FEE = 200;    // 2%
   uint256 private constant BUY_COMMUNITY_REWARD_FEE = 100; // 1%
   // 移除 BUY_BURN_FEE
   ```

3. **添加地址状态变量**
   ```solidity
   address public immutable nodeRewardPool;
   address public immutable communityRewardPool;
   ```

4. **修改构造函数**，添加两个地址参数
   ```solidity
   constructor(
       address _usdt,
       address _router,
       address _staking,
       address _marketingAddress,
       address _nodeRewardPool,
       address _communityRewardPool
   ) {
       // ... 现有代码
       nodeRewardPool = _nodeRewardPool;
       communityRewardPool = _communityRewardPool;
   }
   ```

5. **修改 `_handleBuy` 函数**（第 716-745 行）
   ```solidity
   function _handleBuy(
       address from,
       address to,
       uint256 amount
   ) private notBlacklisted(to) delayedBuyCheck(to) {
       if (
           presaleActive &&
           block.timestamp < presaleStartTime + presaleDuration
       ) {
           revert NotAllowedBuy();
       }

       uint256 nodeRewardFee = (amount * BUY_NODE_REWARD_FEE) / BASIS_POINTS;
       uint256 communityRewardFee = (amount * BUY_COMMUNITY_REWARD_FEE) / BASIS_POINTS;
       uint256 totalFees = nodeRewardFee + communityRewardFee;
       uint256 netAmount = amount - totalFees;

       // 节点分红池
       if (nodeRewardFee > 0) {
           super._update(from, nodeRewardPool, nodeRewardFee);
       }

       // 社区分红池
       if (communityRewardFee > 0) {
           super._update(from, communityRewardPool, communityRewardFee);
       }

       super._update(from, to, netAmount);
       lastBuyTime[to] = block.timestamp;
   }
   ```

6. **更新 `getUSDTAmountForXF` 函数**（第 987 行）
   ```solidity
   uint256 grossXFAmount = (xfAmount * BASIS_POINTS) /
       (BASIS_POINTS - BUY_NODE_REWARD_FEE - BUY_COMMUNITY_REWARD_FEE);
   ```

7. **更新部署脚本**
   - 修改 `scripts/deployAE.js`（或相应的部署脚本）
   - 从配置文件读取新地址并传入构造函数

---

### 方案 B：保留 LiquidityStaking + 新增分红池

**优点：**
- 保留原有的 LiquidityStaking 奖励机制
- 新增节点和社区分红

**缺点：**
- 买入税会增加到 5%（2% LiquidityStaking + 2% 节点 + 1% 社区）
- 税率过高可能影响交易意愿

**实施步骤：**
类似方案 A，但保留原有的 liquidityFee 逻辑，并新增节点和社区分红。

---

### 方案 C：动态分配（可配置）

**优点：**
- 灵活性高，可以后续调整分配比例
- 可以通过治理机制修改

**缺点：**
- 实现复杂度高
- Gas 消耗较高
- 需要额外的权限管理

---

## 关键问题需要确认

1. **地址类型确认**
   - `0x06Ba6DA5d1942DA184ad3E521bC51dfF32D721d9`（节点分红池）
   - `0xeE1285c96E77f2E8CB9C38b66A0BB51b2fCE5537`（社区分红池）
   - 这两个地址是 EOA（外部账户）还是合约地址？
   - 如果是合约，是否有接收代币的逻辑？

2. **LiquidityStaking 影响**
   - 移除 LiquidityStaking 的 BLA 奖励后，是否会影响现有的流动性质押用户？
   - 是否需要保留部分资金给 LiquidityStaking？

3. **总税率确认**
   - 确认总买入税为 3%（2% 节点 + 1% 社区）是否可接受？

4. **已部署合约**
   - 如果 AE 合约已经部署，需要重新部署新合约
   - 需要迁移流动性和用户余额

## 推荐方案

**推荐使用方案 A（简单直接分配）**

理由：
1. 实现简单，代码清晰易维护
2. Gas 消耗最低
3. 资金分配透明，实时到账
4. 符合去中心化理念
5. 取消销毁机制，保持代币总量稳定

**建议总税率：**
- 2% 节点分红池
- 1% 社区分红池
- **总计 3%**

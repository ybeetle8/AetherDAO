# 个人质押门槛等级系统设计方案

## 一、需求概述

### 1.1 核心需求

在现有的团队等级系统基础上，增加**个人质押门槛**作为获得等级的第二个条件。用户的最终等级由两个维度共同决定：

1. **Team KPI（团队业绩）**：下级团队的累计质押总额
2. **个人质押价值**：用户当前的质押金额

**判定规则**：用户最终等级 = min(基于 Team KPI 的等级, 基于个人质押的等级)

### 1.2 设计目标

1. **防止空手套白狼**：要求用户自己也要有足够投入，才能获得高等级
2. **激励个人质押**：鼓励用户在发展团队的同时，也增加自己的质押
3. **公平性**：确保高等级用户既有团队贡献，也有个人投入
4. **系统稳定性**：减少纯推广、不质押的投机行为

## 二、双维度等级体系

### 2.1 完整等级配置表

| 等级 | Team KPI 门槛 (USDT) | 个人质押门槛 (USDT) | 团队奖励比例 |
|------|---------------------|-------------------|--------------|
| V1   | 3,000               | 100               | 3%           |
| V2   | 10,000              | 300               | 7%           |
| V3   | 30,000              | 600               | 11%          |
| V4   | 100,000             | 1,000             | 15%          |
| V5   | 300,000             | 3,000             | 19%          |
| V6   | 1,000,000           | 6,000             | 23%          |
| V7   | 3,000,000           | 10,000            | 27%          |
| V8   | 10,000,000          | 15,000            | 31%          |
| V9   | 30,000,000          | 20,000            | 35%          |

### 2.2 门槛增长规律分析

#### Team KPI 门槛（保持不变）
- 增长规律：约 **3 倍增长**
- 3K → 10K → 30K → 100K → 300K → 1M → 3M → 10M → 30M

#### 个人质押门槛（新增）
- 增长规律：**混合增长**（2x-3x 交替）
- 100 → 300 (3x) → 600 (2x) → 1,000 (1.67x) → 3,000 (3x) → 6,000 (2x) → 10,000 (1.67x) → 15,000 (1.5x) → 20,000 (1.33x)

**设计理念**：
- 初级门槛低（100 USDT），让更多用户能参与
- 中级门槛适中（1,000-6,000），鼓励持续投入
- 高级门槛较高（10,000-20,000），但相对 Team KPI 仍然合理

## 三、等级判定算法

### 3.1 判定流程

```
步骤 1: 检查基础条件
  - 如果是 rootAddress → 等级 = 0

步骤 2: 基于 Team KPI 计算等级
  teamKpiTier = 根据 teamTotalInvestValue 匹配等级

步骤 3: 基于个人质押计算等级
  personalStakeTier = 根据 currentStakeValue 匹配等级

步骤 4: 取两者最小值
  finalTier = min(teamKpiTier, personalStakeTier)

步骤 5: 返回最终等级
  return finalTier
```

### 3.2 伪代码

```solidity
function _getUserTier(address user) private view returns (uint8 tier) {
    // 1. 检查是否是 rootAddress
    if (user == rootAddress) {
        return 0;
    }

    // 2. 获取 Team KPI 并计算对应等级
    uint256 teamKPI = getTeamKpi(user);
    uint8 teamKpiTier = _getTierByTeamKpi(teamKPI);

    // 3. 获取个人质押价值并计算对应等级
    uint256 personalStake = currentStakeValue(user);
    uint8 personalStakeTier = _getTierByPersonalStake(personalStake);

    // 4. 返回两者中的最小值
    return teamKpiTier < personalStakeTier ? teamKpiTier : personalStakeTier;
}

function _getTierByTeamKpi(uint256 teamKPI) private view returns (uint8) {
    IStaking.TeamTier[9] memory tiers = _getTeamTiers();
    for (uint256 i = 0; i < tiers.length; ) {
        if (teamKPI >= tiers[i].threshold) {
            return uint8(9 - i);
        }
        unchecked { ++i; }
    }
    return 0;
}

function _getTierByPersonalStake(uint256 personalStake) private pure returns (uint8) {
    if (personalStake >= 20_000 ether) return 9;  // V9
    if (personalStake >= 15_000 ether) return 8;  // V8
    if (personalStake >= 10_000 ether) return 7;  // V7
    if (personalStake >= 6_000 ether) return 6;   // V6
    if (personalStake >= 3_000 ether) return 5;   // V5
    if (personalStake >= 1_000 ether) return 4;   // V4
    if (personalStake >= 600 ether) return 3;     // V3
    if (personalStake >= 300 ether) return 2;     // V2
    if (personalStake >= 100 ether) return 1;     // V1
    return 0;
}
```

## 四、关键变更点

### 4.1 移除 Preacher 机制

**旧机制**：
- Preacher 门槛：1,000 USDT
- 只有 Preacher 才能获得等级和奖励

**新机制**：
- 移除 Preacher 概念
- 用个人质押门槛替代
- 每个等级都有自己的个人质押要求

**原因**：
1. Preacher 的 1,000 USDT 门槛与 V4 的个人质押门槛重复
2. 新的个人质押门槛体系更细化，覆盖了 Preacher 的功能
3. 简化逻辑，减少冗余判断

### 4.2 等级判定逻辑变更

**旧逻辑**：
```solidity
if (user == rootAddress || !isPreacher(user)) {
    return 0;
}
// 只基于 Team KPI 判定等级
```

**新逻辑**：
```solidity
if (user == rootAddress) {
    return 0;
}
// 基于 Team KPI 和个人质押双维度判定，取最小值
```

### 4.3 奖励分配逻辑变更

**旧逻辑**：
```solidity
if (currentTier > 0 && !tierAllocated[currentTier] && isPreacher(referralChain[i])) {
    // 分配奖励
}
```

**新逻辑**：
```solidity
if (currentTier > 0 && !tierAllocated[currentTier]) {
    // 分配奖励
    // 不再需要 isPreacher 检查，因为等级已经包含了个人质押要求
}
```

### 5.3 修改核心函数

```solidity
/// @notice 获取用户等级（双维度判定）
/// @param user 用户地址
/// @return tier 等级 (0-9)
function _getUserTier(address user) private view returns (uint8 tier) {
    // 1. rootAddress 没有等级
    if (user == rootAddress) {

    uint256 personalStake = currentStakeValue(user);

    // 4. 返回两者中的最小值
    return teamKpiTier < personalStakeTier ? teamKpiTier : personalStakeTier;
}
```

## 六、影响分析

### 6.1 对用户的影响

#### 正面影响
1. **更公平**：防止只推广不投入的行为
2. **更激励**：鼓励用户在发展团队的同时增加个人质押
3. **更清晰**：等级要求更明确，用户知道需要同时满足两个条件

#### 可能的负面影响
1. **门槛提高**：部分用户可能因个人质押不足而等级降低
2. **需要更多投入**：要达到高等级需要更多个人资金

### 6.2 对经济模型的影响

#### 资金池影响
1. **增加质押总量**：用户为了获得高等级，会增加个人质押
2. **减少奖励支出**：部分用户因个人质押不足，等级降低，奖励减少
3. **提高系统稳定性**：更多资金锁定在系统中

#### 激励效果
1. **平衡发展**：用户需要同时关注团队发展和个人投入
2. **长期持有**：为了保持等级，用户需要维持质押
3. **减少投机**：纯推广、不投入的行为被抑制

### 6.3 对代码的影响

#### 需要修改的文件
1. `StakingBase.sol`：核心等级判定逻辑
2. `Staking.sol`：可能需要添加个人质押门槛配置
3. `IStaking.sol`：接口定义（如果需要）

#### Gas 消耗变化
- **增加**：多了一次个人质押等级的计算
- **减少**：移除了 Preacher 检查
- **总体**：变化不大，可能略微增加

## 九、优势分析

### 9.1 相比旧机制的优势

1. **更细化的控制**
   - 旧机制：只有 Preacher (1,000) 一个门槛
   - 新机制：9 个等级，每个等级都有对应的个人质押要求

2. **更公平的分配**
   - 旧机制：只要是 Preacher，就可以获得高等级（只看 Team KPI）
   - 新机制：必须个人投入和团队业绩都达标

3. **更强的激励**
   - 旧机制：达到 1,000 后，个人质押再多也没有额外好处
   - 新机制：个人质押越多，能达到的等级上限越高

4. **更好的风险控制**
   - 旧机制：可能出现"空手套白狼"（个人投入少，团队大）
   - 新机制：高等级必须有相应的个人投入

### 9.2 设计亮点

1. **双维度平衡**：既看团队贡献，也看个人投入
2. **门槛合理**：初级门槛低（100），高级门槛适中（20,000）
3. **逻辑清晰**：取最小值，简单易懂
4. **易于实现**：代码改动不大，逻辑清晰

## 十、总结

3. **减少投机行为**：纯推广、不投入的行为被抑制

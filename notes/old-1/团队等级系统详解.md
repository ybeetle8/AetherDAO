# AetherDAO 团队等级系统详解

## 一、概述

AetherDAO 的团队等级系统是一个基于团队业绩的分级奖励机制。用户通过发展下级团队，累积团队业绩（Team KPI），达到不同等级门槛后，可以在团队成员解质押时获得相应比例的团队奖励。

### 核心特点

- **9 个等级**：V1 到 V9
- **动态计算**：等级根据实时 Team KPI 自动计算
- **差额分配**：高等级成员获得差额奖励，避免重复分配
- **激励机制**：等级越高，奖励比例越高

#### 门槛增长规律
- 采用约 **3 倍增长**规律
- 3K → 10K → 30K → 100K → 300K → 1M → 3M → 10M → 30M
- 使等级提升路径更加平滑和可预测

- 采用 **线性递增 4%** 规律
- 3% → 7% → 11% → 15% → 19% → 23% → 27% → 31% → 35%
- 每提升一级，奖励比例增加 4%

## 三、获得等级的前置条件

### 3.1 必须满足的条件

要获得等级（V1-V9），用户必须同时满足以下条件：

1. **不是 rootAddress**（系统根地址）
2. **必须是 Preacher**（传道者）
   - 条件：当前质押价值 ≥ 1,000 USDT
   - 验证：`currentStakeValue(user) >= PREACHER_THRESHOLD`

**代码位置**：[StakingBase.sol:1253-1256](../contracts/AE-Staking/src/abstract/StakingBase.sol#L1253-L1256)

```solidity
        return 0; // 不满足条件，等级为 0
    }
    // ... 继续判定等级
}
```

### 3.2 Preacher 身份

**定义**：质押价值达到 1,000 USDT 的用户

**重要性**：
- 只有 Preacher 才能获得等级
- 只有 Preacher 才能获得团队奖励
- 如果质押价值低于 1,000 USDT，等级会变为 0

## 四、Team KPI（团队业绩）

### 4.1 定义

**Team KPI = 团队总投资价值 (teamTotalInvestValue)**

这是用户整个下级团队（推荐链，最多 20 层）的累计质押金额总和。

**代码位置**：[StakingBase.sol:670-672](../contracts/AE-Staking/src/abstract/StakingBase.sol#L670-L672)

```solidity
function getTeamKpi(address _user) public view returns (uint256) {
    return teamTotalInvestValue[_user];
}
```

### 4.2 Team KPI 更新机制

#### 质押时增加

当用户质押时：
1. 获取该用户的推荐链（最多 20 层）
2. 将质押金额累加到推荐链上每个地址的 `teamTotalInvestValue`

**代码位置**：[StakingBase.sol:801-817](../contracts/AE-Staking/src/abstract/StakingBase.sol#L801-L817)

```solidity
function _updateTeamInvestmentValues(
    address user,
    uint256 amount,
    bool isIncrease
) internal {
    address[] memory referralChain = getReferrals(user, maxD); // maxD = 20
    for (uint8 i = 0; i < referralChain.length; ) {
        unchecked {
            if (isIncrease) {
                teamTotalInvestValue[referralChain[i]] += amount; // 增加
            } else {
                teamTotalInvestValue[referralChain[i]] -= amount; // 减少
            }
            ++i;
        }
    }
}
```

#### 解质押时减少

当用户解质押时：
1. 获取该用户的推荐链
2. 将解质押的**本金**从推荐链上每个地址的 `teamTotalInvestValue` 中扣除

**注意**：只扣除本金，不扣除利息部分。

#### 绑定推荐人时同步

当用户绑定推荐人时，如果该用户已有质押：
1. 获取新的推荐链
2. 将用户现有的质押金额同步到新推荐链的所有上级

**代码位置**：[StakingBase.sol:819-830](../contracts/AE-Staking/src/abstract/StakingBase.sol#L819-L830)

### 4.3 Team KPI 计算示例

```
假设推荐关系：
A (rootAddress)
└─ B (推荐人)
   └─ C (推荐人)
      └─ D (用户)

当 D 质押 1,000 USDT 时：
- D 的 teamTotalInvestValue 不变（自己的质押不计入）
- C 的 teamTotalInvestValue += 1,000
- B 的 teamTotalInvestValue += 1,000
- A 的 teamTotalInvestValue += 1,000

当 C 质押 5,000 USDT 时：
- C 的 teamTotalInvestValue 不变
- B 的 teamTotalInvestValue += 5,000 (现在是 6,000)
- A 的 teamTotalInvestValue += 5,000 (现在是 6,000)

此时：
- B 的 Team KPI = 6,000 USDT → 等级 V1 (≥3,000)
- C 的 Team KPI = 1,000 USDT → 等级 V0 (不足 3,000)
```

## 五、等级判定算法

### 5.1 判定流程

**代码位置**：[StakingBase.sol:1253-1271](../contracts/AE-Staking/src/abstract/StakingBase.sol#L1253-L1271)

```solidity
function _getUserTier(address user) private view returns (uint8 tier) {
    // 1. 检查前置条件
    if (user == rootAddress || !isPreacher(user)) {
        return 0;
    }

    // 2. 获取用户的 Team KPI
    uint256 teamKPI = getTeamKpi(user);

    // 3. 获取等级配置（从高到低排序）
    IStaking.TeamTier[9] memory tiers = _getTeamTiers();

    // 4. 从最高等级开始匹配
    for (uint256 i = 0; i < tiers.length; ) {
        if (teamKPI >= tiers[i].threshold) {
            return uint8(9 - i); // 返回等级编号
        }
        unchecked {
            ++i;
        }
    }

    // 5. 不满足任何等级
    return 0;
}
```

## 六、等级在奖励分配中的应用

### 6.1 混合奖励分配机制

当用户解质押时，系统会根据推荐链上各成员的等级分配团队奖励。

**核心原则**：
1. **差额分配**：高等级成员获得 (自己等级比例 - 已分配比例) 的奖励
2. **等级唯一性**：每个等级只能被一个成员获得
3. **从下往上遍历**：从直接推荐人开始，向上遍历推荐链
4. **最高 35%**：团队奖励总比例不超过 35%

### 6.2 奖励计算流程

**代码位置**：[StakingBase.sol:1078-1145](../contracts/AE-Staking/src/abstract/StakingBase.sol#L1078-L1145)

```solidity
function _distributeHybridRewards(
    address[] memory referralChain,
    uint8[] memory memberTiers,
    uint256 _interset
) private returns (
    uint256 totalDistributed,
    address[9] memory tierRecipients,
    uint256[9] memory tierAmounts,
    uint8 activeTiers
) {
    bool[10] memory tierAllocated; // 记录哪些等级已被分配
    uint256 cumulativeAllocatedRate = 0; // 累计已分配比例

    // 遍历推荐链（从直接推荐人开始）
    for (uint256 i = 0; i < referralChain.length; ) {
        uint8 currentTier = memberTiers[i];

        // 检查：有等级 && 等级未被分配 && 是 Preacher
        if (
            currentTier > 0 &&
            !tierAllocated[currentTier] &&
            isPreacher(referralChain[i])
        ) {
            uint256 tierRewardRate = _getTierRewardRate(currentTier);
            uint256 actualRewardRate;

            // 计算差额奖励
            if (tierRewardRate > cumulativeAllocatedRate) {
                actualRewardRate = tierRewardRate - cumulativeAllocatedRate;
            } else {
                actualRewardRate = 0;
            }

            if (actualRewardRate > 0) {
                uint256 memberReward = (_interset * actualRewardRate) / PERCENTAGE_BASE;

                if (memberReward > 0) {
                    IERC20(USDT).transfer(referralChain[i], memberReward);
                    totalDistributed += memberReward;

                    tierRecipients[currentTier - 1] = referralChain[i];
                    tierAmounts[currentTier - 1] = memberReward;
                    activeTiers++;
                }

                tierAllocated[currentTier] = true;
                cumulativeAllocatedRate = tierRewardRate;

                // 如果已达到最高等级 35%，停止分配
                if (cumulativeAllocatedRate >= MAX_TEAM_REWARD_RATE) {
                    break;
                }
            }
        }
        unchecked {
            ++i;
        }
    }
}
```

## 七、关键特性总结

### 7.1 等级计算特性

1. **动态更新**：Team KPI 随团队成员的质押/解质押实时更新
2. **深度限制**：最多统计 20 层推荐关系
3. **只计本金**：解质押时只扣除本金，不扣除利息
4. **门槛递增**：等级门槛呈约 3 倍增长
5. **实时判定**：等级根据当前 Team KPI 实时计算，可能升降

### 7.2 奖励分配特性

1. **差额分配**：避免重复奖励，确保公平
2. **等级唯一**：每个等级只能被一个成员获得（先到先得）
3. **优先下级**：从直接推荐人开始分配，保护直推利益
4. **兜底机制**：未分配的奖励转给 rootAddress（营销钱包）
5. **Preacher 验证**：分配时再次验证 Preacher 身份

### 7.3 安全机制

1. **Preacher 验证**：必须有足够质押才能获得等级和奖励
2. **EOA 检查**：防止合约地址作弊（主网启用）
3. **重入保护**：使用 ReentrancyGuard
4. **溢出保护**：使用 unchecked 块优化 gas，但在安全的上下文中

## 十、注意事项

### 10.1 对用户的影响

1. **等级可升可降**：虽然 Team KPI 实时更新，等级会动态变化
2. **需要维护质押**：必须保持 ≥1,000 USDT 质押才能保持 Preacher 身份和等级
3. **推荐关系重要**：绑定推荐人后无法更改（锁定机制）
4. **先到先得**：相同等级的成员，推荐链中位置靠前的优先获得奖励

### 10.2 对开发的影响

1. **Gas 优化**：等级计算在链上进行，需要优化 gas 消耗
2. **数据一致性**：Team KPI 更新必须保证原子性
3. **事件记录**：重要操作需要 emit 事件便于追踪

### 10.3 经济模型考虑

1. **激励机制**：高等级获得更多奖励，激励用户发展团队
2. **公平性**：差额分配确保每个等级都有价值
3. **可持续性**：最高 35% 的团队奖励比例保证系统可持续运行
4. **门槛平衡**：降低初级门槛使更多用户参与，高级门槛保持挑战性
